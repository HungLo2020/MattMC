Identify the next coherent system, subsystem, or meaningful slice of MattMC that should be migrated from Java to Rust. Design, develop, and implement that slice completely in Rust, moving real ownership of that functionality out of Java rather than merely adding a Rust acceleration helper around a Java-owned system. Verify 100% behavioral parity with the existing Java implementation. Given the same inputs and state, the Rust implementation must produce exactly the same externally observable outputs and behavior. Build or extend parity tests and regression coverage as necessary to demonstrate this. Benchmark the migrated implementation through the real production call path, including all Java↔Rust boundary overhead and data movement. Ideally, the migrated implementation should be at least 5% faster than the Java implementation under representative workloads. Performance is important, but the larger goal is the incremental replacement of Java with Rust. Do not chase micro-optimizations solely to reach the 5% target if doing so would make the implementation significantly uglier, less portable, more fragile, overly specialized, or would compromise a clean subsystem boundary. Prefer migrating coherent ownership boundaries rather than isolated hot loops. Where practical, choose the next target so that it naturally reduces Java↔Rust chatter and allows adjacent functionality to move into Rust later. The long-term goal is to replace Java in MattMC entirely, system by system and subsystem by subsystem. Each migration should leave the project architecturally closer to that state while maintaining exact correctness and preferably improving performance.
