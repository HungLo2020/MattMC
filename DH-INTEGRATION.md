## Architecture Overview

### What is Distant Horizons?

Distant Horizons is a Level of Detail (LOD) rendering mod that extends Minecraft's view distance by rendering simplified distant chunks. It consists of:

- **Core module** (~532 Java files): Platform-independent rendering, data structures, and LOD generation logic
- **API module** (included in core): Public API for third-party integration
- **Common module** (~67 Java files): Shared code between mod loaders (Fabric/Forge/NeoForge)
- **Fabric module** (~35 Java files): Fabric-specific integration and platform implementations

**Total source files**: ~634 Java files across all modules

### DH's Build System Requirements

DH uses a sophisticated multi-loader build system that differs significantly from MattMC's approach:

```
DH's Build System:
├── Architectury Loom 1.10 - Multi-loader development environment
├── Fabric Loom 1.10 - Fabric-specific build tooling
├── Manifold Preprocessor - Version-specific code generation
├── SpongeGradle - Access widener processing
├── Shadow Plugin - Dependency shading
└── Forgix - Multi-loader JAR merging
```

```
MattMC's Build System:
├── Standard Gradle Java plugin
├── Custom source sets for Fabric Loader, Sodium, Iris
├── Direct Mojang official mappings (no intermediary)
└── Manual dependency management
```

### Key Architectural Differences

| Aspect | Distant Horizons | MattMC |
|--------|------------------|--------|
| **Mappings** | Mojmap + Parchment (parameter names) | Mojmap only |
| **Mod loader** | Multi-loader (Fabric/Forge/NeoForge) | Fabric only |
| **Build system** | Architectury Loom + plugins | Standard Gradle |
| **Access widening** | Automated via Loom | Manual source modification |
| **Mixin refmaps** | Auto-generated by annotation processor | Not generated |
| **Version support** | Multi-version via preprocessor | Single version |
| **Dependency model** | Fabric API modules required | Integrated into main JAR |

### Integration Challenge Summary

The fundamental challenge is bridging these architectural differences:

1. **Mapping mismatches**: DH expects Parchment parameter names; MattMC uses raw Mojmap
2. **Platform abstractions**: DH's multi-loader code expects platform-specific implementations
3. **Preprocessor directives**: Version-specific code needs preprocessing or manual selection
4. **Fabric API dependencies**: DH requires Fabric API modules that MattMC doesn't include
5. **Build tool differences**: DH's sophisticated build plugins aren't present in MattMC

tasks.register('distantHorizonsJar', Jar) {
    group = 'build'
    description = 'Assembles the Distant Horizons mod JAR'
    
    // Depend on compilation tasks
    dependsOn 'compileDistantHorizonsJava', 'processDistantHorizonsResources'
    
    // JAR naming
    archiveBaseName = 'distanthorizons'
    archiveVersion = '2.3.4-b'
    archiveClassifier = 'mc1.21.10'
    archiveExtension = 'jar'
    
    // Include compiled classes and resources
    from sourceSets.distantHorizons.output
    
    // Output to mods directory
    destinationDirectory = file("${buildDir}/mods")
    
    // Manifest attributes
    manifest {
        attributes(
            'Implementation-Title': 'Distant Horizons',
            'Implementation-Version': '2.3.4-b',
            'Implementation-Vendor': 'jeseibel',
            'Fabric-Loom-Version': '1.10', // For compatibility
            'Fabric-Loom-Mixin-Remap-Type': 'static', // Mixins already applied to source
            'Main-Class': 'com.seibel.distanthorizons.core.jar.JarMain' // For standalone JAR
        )
    }
    
    // Copy fabric.mod.json to JAR root (if it exists)
    doFirst {
        def modJsonSrc = file('modules/distant-horizons-2.3.4b/fabric/src/main/resources/fabric.mod.json')
        if (modJsonSrc.exists()) {
            def modJsonDest = file("${buildDir}/tmp/distantHorizons/fabric.mod.json")
            modJsonDest.parentFile.mkdirs()
            modJsonDest.text = modJsonSrc.text
            from(modJsonDest.parentFile) {
                include 'fabric.mod.json'
            }
        }
    }
    
    // Copy mixin config files
    doFirst {
        def mixinConfigSrc = file('modules/distant-horizons-2.3.4b/fabric/src/main/resources/DistantHorizons.fabric.mixins.json')
        if (mixinConfigSrc.exists()) {
            def mixinConfigDest = file("${buildDir}/tmp/distantHorizons/DistantHorizons.fabric.mixins.json")
            mixinConfigDest.parentFile.mkdirs()
            mixinConfigDest.text = mixinConfigSrc.text
            from(mixinConfigDest.parentFile) {
                include 'DistantHorizons.fabric.mixins.json'
            }
        }
    }
}

// Copy DH JAR to run/mods/ directory
tasks.register('copyDistantHorizonsJar', Copy) {
    dependsOn 'distantHorizonsJar'
    from "${buildDir}/mods/distanthorizons-2.3.4-b-mc1.21.10.jar"

### Step 2.2: Handle Platform-Specific Code

**Problem**: DH uses Architectury's multi-loader system with platform-specific implementations. Your Fabric-only build needs Fabric implementations.

**What to look for**:
```java
@ExpectPlatform
public static SomeType getPlatformImpl() {
    throw new AssertionError();
}
```

The `@ExpectPlatform` annotation tells Architectury to find platform-specific implementations in:
- `fabric/src/main/java/...platform/fabric/`
- `forge/src/main/java/...platform/forge/`
- `neoforge/src/main/java/...platform/neoforge/`

**Solution approach**:

1. **Find all @ExpectPlatform methods**:
```bash
cd modules/distant-horizons-2.3.4b
grep -r "@ExpectPlatform" --include="*.java" -n
```

2. **Verify Fabric implementations exist**:
For each @ExpectPlatform method, ensure there's a corresponding implementation in the `fabric/` directory.

3. **Manual stub creation** (if implementations are missing):

If a Fabric implementation doesn't exist, you'll need to create it:

```java
// In common code:
package com.example.common.platform;
@ExpectPlatform
public class PlatformHelper {
    public static String getPlatformName() {
        throw new AssertionError();
    }
}

// Create in fabric code:
package com.example.fabric.platform;
public class PlatformHelperImpl {
    public static String getPlatformName() {
        return "Fabric";
    }
}
```

**Known platform abstractions in DH**:

- Configuration screen registration
- Keybinding registration  
- Resource pack access
- Networking layer

## Known Issues and Challenges

### Critical Issues

#### 1. Parchment Parameter Name Mismatches

**Severity**: HIGH  
**Impact**: Prevents compilation  
**Effort to fix**: 10-20 hours

**Problem**: DH source code references method parameters by name (from Parchment mappings). Your Mojang-only mappings use generic names like `var1`, `var2`, etc.

**Example**:
```java
// DH code expects:
public void render(Camera camera, float partialTicks, boolean updateFrustum) {
    setupCamera(camera, partialTicks);
}

// But Mojang mappings have:
public void render(Camera var1, float var2, boolean var3) {
    setupCamera(var1, var2); // Won't compile - 'partialTicks' doesn't exist
}
```

**Solutions**:
1. Add Parchment to your build (requires significant refactoring)
2. Manual find-and-replace for all parameter name mismatches (tedious)
3. Use IDE refactoring tools to automate some of the work

**Recommendation**: Budget significant time for manual fixes.

#### 2. Fabric API Module Dependencies

**Severity**: HIGH  
**Impact**: Runtime errors if missing  
**Effort to fix**: 2-4 hours

**Problem**: DH relies on several Fabric API modules that may not be in your project:

- `fabric-api-base` - Base Fabric API hooks
- `fabric-lifecycle-events-v1` - Lifecycle event system
- `fabric-resource-loader-v0` - Resource pack loading
- `fabric-rendering-v1` - Rendering hooks
- `fabric-networking-api-v1` - Networking layer
- `fabric-entity-events-v1` - Entity event hooks
- `fabric-command-api-v2` - Command registration

**Solutions**:
1. Add all required Fabric API modules as dependencies (Step 1.4)
2. Verify versions match your Minecraft version
3. Ensure they're in the runtime classpath

**Recommendation**: Use Fabric API's bundled JAR or individual modules.

#### 3. Missing Mixin Refmaps

**Severity**: MEDIUM  
**Impact**: Potential runtime failures, breaks on MC updates  
**Effort to fix**: N/A (architectural limitation)

**Problem**: Your build doesn't run the Mixin annotation processor, so refmaps aren't generated. This means:

- Mixins target classes by hardcoded names
- No automatic remapping when mappings change
- More fragile across Minecraft versions

**Solutions**:
1. Accept the limitation (works with `-Dfabric.development=true`)
2. Add Mixin annotation processor to your build (complex)
3. Keep `-Dfabric.development=true` enabled to allow lenient mixin handling

**Recommendation**: Accept the limitation for now. Keep development mode enabled.

### Medium Issues

#### 4. Architectury Platform Abstractions

**Severity**: MEDIUM  
**Impact**: May prevent compilation of platform-specific code  
**Effort to fix**: 8-16 hours

**Problem**: DH uses Architectury's `@ExpectPlatform` pattern for multi-loader support. Your Fabric-only build needs Fabric implementations for all platform calls.

**Solutions**:
1. Verify Fabric implementations exist for all @ExpectPlatform methods
2. Create stub implementations if missing
3. Remove or comment out platform code that isn't needed

**Recommendation**: Audit all platform code systematically.

#### 5. Manifold Preprocessor Directives (✅ RESOLVED)

**Status**: ✅ **COMPLETED** - All preprocessor directives removed

**Work completed**:
- 75 files processed (25 Fabric + 50 Common)
- ~427 preprocessor blocks removed
- All #if, #else, #endif, #elif directives eliminated
- Code paths selected for MC 1.21.10

**Approach used**: Manual directive removal

**Verification**: Zero active directives remaining in Fabric and Common modules

### Low Issues

#### 6. Resource Loading Paths

**Severity**: LOW  
**Impact**: Missing textures/configs  
**Effort to fix**: 1-2 hours

**Problem**: Resource file paths may not match your project structure.

**Solutions**:
1. Ensure all resource directories are in the source set
2. Test resource loading at runtime
3. Fix any path mismatches in resource loading code

#### 7. Config File Format

**Severity**: LOW  
**Impact**: Config not loading/saving  
**Effort to fix**: 1-2 hours

**Problem**: DH uses TOML for config files. Ensure Night Config is properly integrated.

**Solutions**:
1. Verify Night Config dependency is in classpath
2. Test config file creation at runtime
3. Check logs for config loading errors

### Architectural Limitations

These are inherent to your integration approach and can't be easily fixed:

1. **No mixin refmaps**: Mixins use direct class names
2. **Development mode required**: Must keep `-Dfabric.development=true`
3. **Single version support**: No multi-version compatibility
4. **Manual access wideners**: Future DH updates require reapplication
5. **No intermediary mappings**: Direct Mojang mappings only
6. **Source-level integration**: Not a "true" mod architecture

**Impact**: These limitations mean:
- More fragile across Minecraft updates
- Can't use official DH releases directly

- Higher maintenance burden for updates

**Mitigation**:
